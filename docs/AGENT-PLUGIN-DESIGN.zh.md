## 0. 一页纸摘要

现在这个插件（0.2.1）是**死插件**：界面里写死了「输入路径 → 探测 → 表格 → 改值」这套流程，换一款游戏、换一种存档格式，界面就废了。

用户要的是**对话型 / agent 型**插件：用户用人话说需求，模型决定怎么查、查什么、改哪里，界面只负责把模型查到的东西**显示出来**、把用户的操作**传回去**。

因此 0.3 的核心变化只有一句话：

> **界面不持有任何游戏知识；它渲染的是「模型这次会话产生的结构化结果」。**

由此推出四个必须成立的性质：

1. **能力层确定性**：解密、改字节、备份、回读校验，全部是死代码。模型不能即兴改字节。
2. **语义层可沉淀**：我不知道的字段，现场查（反汇编 / 本地化资源 / 试探）；查清后写进知识库，下个会话直接命中。
3. **写入单入口**：不管是模型调工具还是用户在界面上点按钮，走的是同一个写函数——备份 → 改 → 回读校验 → 回报。

右侧抽屉因此退化成「一个读者」：给定存档路径，解档 + 套知识库，渲染成一篇带小标题的文档（像渲染好的 markdown）。它不订阅会话、不存状态，所以刷新不丢、也不会与对话不同步。
4. **经验不随会话消失**：会话是隔离的，知识不是。格式指纹、游戏档案、改过的操作配方都进知识库，换个会话、换款游戏照样能用上。

## 1. 现状与差距

### 1.1 现状（0.2.1）

| 组件 | 内容 | 问题 |
|---|---|---|
| `scripts/gmtool.py` | `probe` / `scan` / `save dump,get,set,add,remove` / `proto` / `dll types,dis,xref,patch` / `__doctor__` | 能力层已经够用 |
| 9 个 `gm_*` 工具 | 模型可调，返回纯文本 | **只返回文本**，界面拿不到结构化结果 |
| `src/routes.js` | 8 条 `POST /api/gm/*` 路由，供面板调用 | **面板自己也能写档** → 与工具形成第二套入口 |
| `client.js` | 全局面板里的「存档修改」页：体检 / 路径 / 探测 / 表格 / 应用 | 与当前会话无关，**换会话就断片** |

### 1.2 差距

- 面板是**全局**的，用户要求「每个会话单独处理自己的」。
- 面板与对话**不共享状态**：模型改了档，面板不知道；面板改了档，模型不知道。
- 「含义」缺失：只显示 `405` 和数字，不显示「已解锁升级项」。

## 2. 设计原则

### 2.1 三层责任

| 层 | 谁负责 | 判定标准 |
|---|---|---|
| 能力层 | `gmtool.py`（确定性代码） | 会不会破坏文件？会 → 必须是死代码 + 校验 |
| 语义层 | 模型 + 知识库 `games/<key>.json` | 换款游戏是否要改代码？要 → 不能进代码 |
| 对话层 | 模型 + 用户 | 是否需要理解人话？是 → 不能进代码 |

### 2.2 三条硬规则

1. **写路径唯一**。任何写操作最终都落到 `core.applyChanges(path, changes)` 一个函数上。
2. **界面无分支**。`client.js` 里不允许出现任何游戏名、字段号、枚举值的判断。
3. **没验证不算完**。写盘后必须重新解析并逐字段比对，只允许目标字段变化。

## 3. 目标形态

### 3.1 右侧抽屉（`rightbar.session`，每会话独立）

```
┌─ 存档工作台 ─────────────────────┐
│ 目标  slot_0.mp                  │
│       AES-128-CBC + LZ4 + msgpack│
│       41.4 KB · 今天 16:02        │
│       [换一个] [重新扫描]          │
│                                  │
│ 这个存档里有什么                   │  ← 首次探测后自动生成（gm_brief）
│  · 进度   第 42 天 · 累计 10.4 小时│
│  · 资源   金币 888888 · 木头 9994 │
│  · 解锁   升级 98 项 · 建筑 112 项 │
│  · 队伍   15 个信徒               │
│                                  │
│ 建议怎么改                         │
│  · 635 未解锁 → 五角星用不了       │
│    [改这个] [先别动]               │
│  · 783 未完成 → 羊绒仙境引导半截   │
│    [改这个]                       │
│                                  │
│ 已查明的结构                       │
│  ▸ 405 UnlockedUpgrades  98 项   │
│     已解锁升级（枚举 UpgradeSystem.Type）│
│  ▸ 1162 items                    │
│     资源库存，元素 [类型, 数量, 0]  │
│     金币 888888 · 木头 9994       │
│  ▸ 1109 Followers  15 个          │
│     信徒，每个 192 个元素          │
│   ……（未查明的显示「?」，可点「问这是什么」）│
│                                  │
│ 待确认的修改                       │
│  ☐ 635 → True  解锁基地传送台      │
│     [执行] [为什么要改]            │
│                                  │
│ 最近操作                          │
│  16:02 备份 → …\backup_2026…      │
└──────────────────────────────────┘
```

**要点**：抽屉是「算出来的」，不是「攒出来的」。它按存档内容 + 知识库实时生成这份文档；知识库里没有的，落到最后的「还没查明」一栏，而不是编一个解释。

### 3.2 消息流内联卡片（`tool.call.toolview`）

`gm_probe` / `gm_brief` / `gm_save_list` / `gm_save_apply` 四个工具注册自定义卡片：

- `gm_probe`：一行摘要（格式链 + 大小） + 「打开工作台」
- `gm_save_list`：前 6 行 + 「查看全部」，点击展开到右栏
- `gm_save_apply`：变更清单 + 备份路径 + 校验结果（红/绿）

作用是把「我查了什么」留痕在对话里，回看历史能看懂，而不是一串 JSON。

### 3.3 交互路径

| 用户行为 | 走向 |
|---|---|
| 「帮我看看存档」「我在玩咩咩启示录」 | 模型调 `gm_scan` → 候选列表 → 用户挑 → `gm_probe` → `gm_brief`（概览 + 建议）→ 抽屉亮起 |
| 贴一个路径 | 模型 `gm_probe` → `gm_save_list` → 抽屉亮起 |
| 「金币改成 9999」 | 模型 `gm_save_apply`（备份+校验）→ 抽屉与卡片同步更新 |
| 抽屉里点「执行」 | 走**同一个** `core.applyChanges`，结果同时写回抽屉 |

### 3.4 全局面板：历史改过的游戏（保留并改造）

0.2.1 的全局面板不删，改成**跨会话的样子**：它记的不是会话状态，而是 `history.json` 里的历史。

```
┌─ 存档修改 ─────────────────────────────┐
│ 改过的游戏                              │
│  咩咩启示录        最近 18:39 · 改过 3 次│
│    slot_0.mp · 41.4 KB                 │
│    [继续改] [看历史] [打开所在文件夹]     │
│  鸭科夫            最近 11-07 · 改过 1 次│
│    Save_1.sav · 72.6 KB (明文 JSON)     │
│  ─────────────────────────────────     │
│  [扫描存档] [体检环境] [知识库]           │
└─────────────────────────────────────────┘
```

三条原则：

1. **它只读 `history.json`**，不参与写档流程——写档永远走会话里的 `apply`。
2. 「继续改」的动作是**开一个会话并把上下文交给模型**，而不是自己弹编辑器。因为版本差异（游戏更新、存档结构变了）只有模型能现场判断。
3. 「知识库」入口列出 `formats.json` 与 `games/*.json` 的条目，允许查看/删除错记的经验。

## 4. 架构：两个读者，同一份事实源

抽屉**不订阅会话、不存会话状态**。它直接读「存档文件 + 知识库」，把内容渲染成一篇看得懂的说明文档；模型也读写同样这两份东西（调工具、改档）。两边在文件系统上天然一致，不需要任何同步机制。

```
            用户说话
               │
               ▼
    ┌──────────────────────┐
    │ 模型（会话）          │  判断 / 查证 / 改档
    └──────┬───────────────┘
           │ gm_* 工具
           ▼
    ┌──────────────────────┐            ┌──────────────────┐
    │ 宿主：工具实现        │──── 写 ───▶│ knowledge/        │
    └──────┬───────────────┘            │ 格式指纹 / 字段含义 │
           │ 改档                        │ 操作配方 / 历史     │
           ▼                            └────────┬─────────┘
    ┌──────────────────────┐                     │ 读
    │ 存档文件（唯一事实源）│◀────────────────────┘
    └──────┬───────────────┘
           │ 读
           ▼
    ┌──────────────────────┐
    │ POST /api/gm/overview │  纯渲染：解档 + 套知识库 → 文档模型
    └──────┬───────────────┘
           ▼
    ┌──────────────────────┐
    │ 右栏抽屉 / 内联卡片    │  只排版，不含业务判断
    └──────────────────────┘
```

三条推论：

1. **不需要会话状态层**。抽屉只需要知道「现在看哪个文件」——路径存 `sessionStorage`（每会话一份），或由 `gm_brief` 的返回值带过来。
2. **刷新不丢**。文档是算出来的，不是攒出来的。没有"状态没同步"这类 bug 的生存空间。
3. **对话仍是主驱动**。需求变了 → 我改文件 / 补知识库 → 抽屉下次取数就变了。

### 4.1 文档模型：返回「一篇文档」，不是字段树

```jsonc
{
  "title": "咩咩启示录 · slot_0",
  "subtitle": "41.4 KB · 今天 16:02 · AES-128-CBC + LZ4 + msgpack",
  "sections": [
    { "type": "stats", "heading": "概览",
      "items": [ { "k": "进度", "v": "第 42 天" }, { "k": "游戏时长", "v": "10.4 小时" } ] },
    { "type": "table", "heading": "资源",
      "columns": ["物品", "数量"],
      "rows": [ ["金币", "888888"], ["木头", "9994"] ] },
    { "type": "list", "heading": "已解锁的关键内容",
      "items": ["基地传送台", "熔炉", "复活 / 饥饿 / 无所不在"] },
    { "type": "unknown", "heading": "还没查明的 12 项",
      "items": [ { "k": "1109", "v": "15 个元素" } ] }
  ]
}
```

前端只认三种排版单元：`stats`（键值对）、`table`（表格）、`list`（列表）——排版成一篇带小标题的文档，像渲染好的 markdown。**没有树、没有通用编辑器**；要看某个字段的原始字节结构，用对话让我展开。

### 4.2 未知项怎么变成已知

「还没查明的 12 项」里点一条，生成一句话「**1109 是什么？**」发给我。我反汇编 / 查本地化资源 / 试探后写进 `games/<key>.json`，下次渲染那一行就变成「队伍 · 15 个信徒」。

这是抽屉**唯一会主动说话**的按钮，其余都靠你直接跟我说。

### 4.3 缓存

`overview` 是重操作（40 MB 存档要解密 + LZ4 + msgpack + 套知识库）。缓存键 = `(path, size, mtime, knowledge 目录 mtime)`，命中就直接返回；改档或改知识库会自动失效。

## 5. 接口契约

### 5.1 工具层（模型调）

沿用现有 9 个工具，**只改返回值**：从纯文本改为

```jsonc
{ "text": "<给人看的一段话>", "data": { /* 结构化，供界面渲染 */ } }
```

`gm_save_list` 的 `data` 形如：

```jsonc
{ "kind": "table", "path": "405",
  "title": "UnlockedUpgrades · 已解锁升级 98 项",
  "columns": ["值", "含义"],
  "rows": [{ "path": "405.0", "value": "54", "label": "Ability_Eat（饥饿）", "leaf": true }],
  "parents": [["根", ""], ["405", "405"]] }
```

新增 3 个工具：

| 工具 | 作用 |
|---|---|
| `gm_brief` | **首次拿到存档必调**。扫一遍结构，产出「这个存档里有什么」+「建议怎么改」。输出分两半：给人看的概览，给界面渲染的分组卡片（进度 / 资源 / 解锁 / 队伍 / 风险点） |
| `gm_knowledge` | 读写知识库：`op: get\|set\|list`，`kind: format\|game\|operation`。按游戏 key 存取格式指纹、字段含义、操作配方 |
| ~~`gm_semantics`~~ | 合并进 `gm_knowledge` |

### 5.2 宿主路由（界面调）

分两类，**写只有一条**：

| 路由 | 类型 | 说明 |
|---|---|---|
| `POST /api/gm/doctor` | 读 | 体检 |
| `POST /api/gm/install` | 读 | 装缺失依赖（不改存档） |
| `POST /api/gm/scan` | 读 | 扫描候选存档 |
| `POST /api/gm/probe` | 读 | 探测格式链 |
| `POST /api/gm/list` | 读 | 列字段 |
| `POST /api/gm/overview` | 读 | 解档 + 套知识库 → 返回一篇文档模型（见 4.1），供抽屉渲染 |
| `POST /api/gm/history` | 读 | 历史改过的游戏列表（供全局面板做快速跳转） |
| **`POST /api/gm/apply`** | **写** | **唯一写入口**；游戏运行中需带用户确认，见 7.4 |
| ~~`/api/gm/get`~~ | — | 合并进 `list` |

`/api/gm/apply` 请求体：

```jsonc
{ "path": "C:\\…\\slot_0.mp",
  "changes": [{ "op": "set", "target": "635", "value": true }],
  "sessionId": "…", "dryRun": false }
```

响应体：

```jsonc
{ "ok": true,
  "backup": "…\\saves\\backup_manual_20261108-160211",
  "before": { "size": 42481, "sha256": "…" },
  "after":  { "size": 42481, "sha256": "…" },
  "diff": ["635"],
  "verified": true }
```

### 5.3 客户端席位

| 席位 | 用途 |
|---|---|
| `rightbar.session` | 存档说明书抽屉（single / session 作用域，宿主已按会话隔离；内容来自 `/api/gm/overview`，与对话无关） |
| `tool.call.toolview`（key = `gm_probe` / `gm_brief` / `gm_save_list` / `gm_save_apply`） | 消息流内联卡片 |
| `conversation.chat.turnTail` | 写入结果落在轮次尾部（摘要 + 备份路径） |
| `sidebar.panellist` + `main` | 全局面板：历史改过的游戏、扫描、体检、知识库（0.2.1 已有的席位，继续用） |

> 已确认 `rightbar.session` 的 ownerProps 为 `{ width, viewportWidth, canShow, active, retainTab }`；`rightbar` 整体是 single 槽位，`replaceRisk: "shadows-shipped-ui"`，**只注册自己不替换别人的**。

## 6. 知识层：语义 + 经验

会话是隔离的，知识不是。这一节定义四样东西——字段含义、格式指纹、操作配方、改档历史——它们全部落盘、跨会话复用，并且**由工具在干活时自动写入**，不靠人肉维护。

### 6.1 标注三层

| 层 | 来源 | 何时产生 | 展示 |
|---|---|---|---|
| L1 自动 | 字段名、类型、枚举名（从 DLL 常量表导出） | 探测时 | 「405 UnlockedUpgrades · 数组」 |
| L2 词典 | 曾经查清并写入 `games/<key>.json` | 首次查清 | 「已解锁升级项（UpgradeSystem.Type）」 |
| L3 未知 | 都没有 | — | 「? 需要查」+ 按钮「问这是什么」 |

L3 按钮做的事：在对话里生成一条消息「405 里第 3 项是 421，这是什么？」——我现场反汇编/查本地化资源，得出结论后写回 L2。**这就是 agent 与死插件的分界线**。

### 6.2 三个存储

| 存储 | 内容 | 谁写 | 复利方式 |
|---|---|---|---|
| `formats.json` | **格式指纹**：头部魔数、加密方式、key 从哪来、压缩链、以及「怎么验证这个判断」 | 首次破解成功时自动追加 | 下次遇到同款格式，`gm_probe` 直接命中，不用再猜 AES 头布局 |
| `games/<key>.json` | **游戏档案**：存档路径、格式引用、字段含义、已验证的操作配方 | 查清一个字段 / 验证一次操作就写一条 | 新会话一上来就知道「咩咩启示录的 635 = 基地传送台」 |
| `history.json` | **改档历史**：时间、游戏、文件、改动、备份路径、校验结果 | 每次 `/api/gm/apply` 成功都写 | 全局面板据此列「历史改过的游戏」，点一下跳过去 |

三者都放在同一目录、彼此引用（`games/<key>.json` 用 `format: "aes-cbc-lz4-msgpack"` 指向 `formats.json` 的一条）。

### 6.3 存放位置

```
C:\Users\Administrator\.dsh\skills\game-modding\knowledge\
  formats.json            格式指纹库（跨游戏共用）
  games\
    cult-of-the-lamb.json 游戏档案
    ...
  history.json            改档历史
```

放在技能目录而不是插件里，原因：

- 我每个会话都能读（跨会话复利）；
- 插件发布时不必带上别人的私有知识；
- 用户也能手改。

### 6.4 游戏档案结构

```jsonc
{
  "game": "cult-of-the-lamb",
  "match": { "pathContains": ["Massive Monster", "Cult Of The Lamb"], "format": "aes128cbc+lz4+msgpack" },
  "format": { "header": "0x45", "cipher": "AES-128-CBC", "key": "salt(16) 明文", "wrap": "Lz4BlockArray" },
  "fields": {
    "405": { "name": "UnlockedUpgrades", "desc": "已解锁升级项", "type": "List<UpgradeSystem.Type>",
             "enumRef": "upgrade_types.json", "notes": "含 Ability_Eat(54)/Resurrection(59)/TeleportHome(142)" },
    "1162": { "name": "items", "desc": "资源库存", "type": "List<[ITEM_TYPE, qty, 0]>",
              "enumRef": "item_types.json" },
    "1109": { "name": "Followers", "desc": "信徒", "type": "List<192 元素>", "notes": "元素结构见 followers.md" }
  },
  "operations": [
    { "id": "unlock-base-teleporter", "desc": "解锁基地传送台（五角星）",
      "changes": ["set 635=True"], "verified": true, "date": "2026-11-08" }
  ]
}
```

`operations` 是复利的关键：下次用户说「我五角星不能用」，我直接命中这条，不用重新反汇编。

`formats.json` 的一条长这样：

```jsonc
{
  "id": "aes-cbc-lz4-msgpack",
  "match": { "firstByte": "0x45", "mod16": -33 },
  "layout": [ { "kind": "aes128cbc", "headerBytes": 1, "keyFrom": "next16", "ivFrom": "next16" },
              { "kind": "lz4blockarray" },
              { "kind": "msgpack" } ],
  "verify": "解密后首字节应为 0x90 或 0xdc（msgpack 数组），且长度能被完整解析",
  "sources": ["Cult of the Lamb slot_0.mp"],
  "notes": "key 就是明文 salt，IV 紧随其后；四件套（slot/meta/persistence/settings）同一套格式"
}
```

里面有 `verify` 字段是刻意的：**知识必须带上「怎么证伪」**，否则下个会话可能把错误经验当真理用。

### 6.5 记录纪律

自动记录的边界（这是防止知识库被污染的关键）：

| 该记 | 不该记 |
|---|---|
| 已验证的解密链路（能完整解出、能重新写回） | 「试了 AES，好像是这个 key」这类猜测 |
| 逐字段比对确认过的差异（只变了 635） | 没做回读校验的改动 |
| 查证过的字段含义（反汇编 / 本地化资源 / 实测三选一以上） | 从字段名猜的含义 |
| 用户确认过的操作配方（如 `635=True` 修好五角星、`394 += 411` 让熔炉出现在建造菜单） | 试错中间态 |

每条记录带 `source` 与 `date`，界面上区分显示「自动标注 / 查证 / 用户确认」。

## 7. 关键流程

### 7.1 首次接触一款游戏

```
用户：我在玩 XXX / 帮我看看存档
 → gm_scan（扫描候选，按「当前档/备份」分级）
 → 用户点选 → gm_probe（格式链）+ gm_save_list（顶层字段）
 → 抽屉亮起，显示 L1 标注
 → 我读 knowledge/games/<key>.json：没命中 → 视为新游戏
```

### 7.2 「这个字段是什么」

```
用户：405 里这些数字是什么
 → gm_save_list 405（data.data 里带枚举名，若有 enumRef）
 → 缺失则：gmtool enum / gmtool dll dis / 本地化资源检索
 → 结论写回 games/<key>.json（gm_knowledge set）
 → 抽屉里那行从「98 项」变成「已解锁升级 98 项（含熔炉/复活）」
```

### 7.3 改档

```
用户：金币改成 9999
 → 定位：查 semantics / list 找到 1162 里的 [20, 888888, 0]
 → 提议：pending 里出现一条（若风险高则等用户确认）
 → gm_save_apply → core.applyChanges:
      ① 路径校验（存在、非备份、游戏未运行）
      ② 自动备份到 saves\backup_manual_<时间戳>
      ③ 字节级同宽度替换
      ④ 重新解密解析，逐字段比对（只允许目标字段变化）
      ⑤ 失败则回滚并报错
 → 回报：备份路径 + before/after sha256 + 差异字段
 → 抽屉 history 追加一行，卡片变绿
```

### 7.4 游戏正在运行（两步同意）

写档前 `tasklist` 检测游戏进程（如 `Cult Of The Lamb.exe`）。**正在运行则默认拒绝**，理由是退出时游戏会用内存里的旧数据覆盖文件，改动白做甚至更糟。

拒绝时返回结构化结果，而不是一句错误：

```jsonc
{ "ok": false, "code": "GAME_RUNNING", "process": "Cult Of The Lamb.exe",
  "message": "游戏正在运行，退出后才能写入；否则退出时会被内存数据覆盖。",
  "options": [ { "id": "user-confirmed", "label": "仍要写入（我已知晓）" },
               { "id": "cancel", "label": "算了" } ] }
```

用户明确说「我知道，写吧」之后，我才用 `consent: "user-confirmed"` 重试一次。**没有命令行 `--force` 这种绕过口子**——同意必须来自人，且每次都要。同意记录写进 `history.json`。

## 8. 不变量与安全

| # | 不变量 | 违反时 |
|---|---|---|
| 1 | 写盘前必有备份，备份路径必须回报给用户 | 中止 |
| 2 | 写盘后必须重新解析成功 | 回滚 |
| 3 | 逐字段比对，差异集合 ⊆ 请求的变更集合 | 回滚 |
| 4 | 单次只动一个存档文件 | 中止 |
| 5 | 不改「备份文件」与「非存档文件」 | 拒绝 |
| 6 | 游戏运行中默认不写 | 拒绝，返回 `GAME_RUNNING`，需用户明确同意后重试 |
| 7 | 非 loopback 请求一律 403 | 拒绝 |
| 8 | 知识库只记录已验证的经验（见 6.5） | 拒写该条 |

## 13. 上下文成本（实测）

用户关心的是「不用它的时候，会不会白占上下文」。实测（2026-11-08，0.2.1 的 9 个工具）：

| 项 | 常驻开销 | 说明 |
|---|---|---|
| 9 个 `gm_*` 工具定义 | **≈ 1507 tokens** | 每轮都在：名字 + 描述 + 参数 schema |
| 技能目录条目 `game-modding` | ≈ 110 tokens | 只有 `name` + `description` 进目录 |
| `SKILL.md` 正文 | 0 | 触发时才加载 |
| 右栏抽屉 / 全部 UI 代码 | **0** | 纯客户端，模型看不见 |
| `knowledge/*.json` | 0 | 我不读就不进上下文；读也只读当前游戏那一份 |

结论要说清楚：**不用它的会话里，它不是 0，是约 1.6K tokens / 轮。**

### 13.1 可选的省法（按收益排序）

| 方案 | 预计常驻 | 代价 |
|---|---|---|
| `tools: "compact"`：9 个合并成 4 个（`gm_probe` / `gm_save` / `gm_dll` / `gm_meta`），描述压到一行 | ≈ 400–600 | 工具粒度变粗，参数变多 |
| 只精简描述，不合并 | ≈ 700–900 | 无功能损失 |
| `tools: "none"`：一个都不注册，全靠 `SKILL.md` + bash 调 `gmtool.py` | **0** | 每次要手拼命令行；界面与工具脱钩 |
| 插件管理里直接禁用 | 0 | 用之前要手动开 |

插件新增配置项：

```jsonc
{ "tools": "compact" }   // full | compact | none，默认 compact
```

`compact` 也顺带解决另一个问题：工具越少，我选错的概率越低。

### 13.2 设计上的一处提醒

UI 是免费的，工具是收费的。所以「把能力都做进界面」对上下文友好，但违背第 2 节的原则（界面不能持有游戏知识）。两者的平衡点就是 `compact`：**保留真正需要模型判断的那几个入口，其余能力沉到 `gmtool.py` 的命令行里**——命令行只有我调用时才产生 token。
